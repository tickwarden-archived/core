# Datapack archive EOL — experimental, do not deploy

This is an offline prototype, not a release or a security boundary. Original sources remain frozen and the generator never modifies them. It does not retire mods. The migration manifest identifies copied upstream files and commits; copies do not remove upstream repositories or stop existing installations. No generated pack has been verified on a Minecraft server.

The intended lifecycle is relative to observed server ticks: 0–5,183,999 warning; 5,184,000–12,095,999 restricted functions; at 12,096,000 lock and best-effort scheduled function cleanup. Those are 72/168 hours only at 20 TPS; lower TPS, downtime, pause-when-empty and disabled tick tags extend wall-clock time. Versions get separate scoreboard identifiers using the supplied versioned pack ID; reuse of an ID shares state. Lifecycle state lives in world scoreboard and storage; resetting it or a privileged operator bypasses this mechanism. Removing the objective without its storage marker is not self-healing. An initial objective collision may log an error; repeated reloads should not re-add the objective when the marker persists. Notices are sent on first load and phase changes, not every reload; players who were offline can miss notices.

The restriction only wraps .mcfunction commands, and even that has not been validated against every Minecraft version or command behavior. Non-function features (advancements, loot tables, recipes, predicates, dialog actions), command blocks, operators, other datapacks, external APIs and scoreboard edits are not restricted. This is not world-wide read-only, not an access-control system, and not a defense against hostile packs. A function is allowed during phase 2 only if every non-comment command matches the very narrow read-only allowlist; mixed read/write functions are blocked in their entirety. Lifecycle scores, storage and tellraw remain writable. Guard wrapping may change execution semantics, notably macros, returns, execution context and function results; do not use until version-specific server tests prove compatibility.

Cleanup attempts to clear only statically detected literal internal schedule targets. The detection is incomplete (including dynamic macro targets); the manifest reports this explicitly. Namespaced function identifiers may be shared across packs, so even these schedule clears require ownership review before deployment. It does not erase persistent data. Unknown ownership must not trigger deletion.

Backslash line continuation is rejected rather than transformed, pending parser and runtime validation. Unsupported or mixed function layouts are rejected. Outputs are staged and published only after validation; failures remove the stage. UTF-8 is explicit and only newline characters split commands. Source hashes and paths are compared before publication, although concurrent modification after that comparison cannot be ruled out: run on an immutable snapshot.

An audit across the current 15 distinct core/vortex packs produced 9 unvalidated prototypes and rejected 6, including both vortex versions. These are diagnostics, not deployable packs. Historical differences are preserved under archived/historical, while embedded mod resources are intentionally excluded from retirement. Complete per-version entry-point/resource review, continuation support, real-server integration tests and safe upstream migration remain necessary before publishing or rollout.

Vanilla datapacks cannot execute shell commands or arbitrarily access operating-system files on their own. Commands may damage world data or socially engineer players; installed mods/plugins that expose command bridges, or software vulnerabilities, can change the threat model.
